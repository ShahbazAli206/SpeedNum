2 Decisions only you can make

These change the shape of the build. I've picked the lower-effort default in each case — flag if you want the other branch.

Are seats one shared pool (staff + clients together) or two separate pools? Your wording says "seats for staff… and clients," which could mean either. A single pool ("20 seats total, use them however") is simpler to build and explain; two pools ("10 staff seats + 50 client seats") matches how most accounting-practice tools price it, since clients vastly outnumber staff. Default assumed below: two separate pools (staff seats, client seats) — it maps more naturally onto how you'd actually price this.
Fully free-form custom roles, or a fixed richer set of built-in roles with configurable permissions? Free-form (owner types any role name, e.g. "Junior Bookkeeper") needs a role-designer UI, name-collision handling, and more validation. A fixed set — Owner, Admin, Manager, Clerk Admin, Accountant, User, Viewer — covers every role you named in the scenario and only needs a permission-toggle UI, not a role-builder. Default assumed below: fixed built-in role set with per-role permission toggles. Free-form naming can be layered on later without redoing the underlying permission engine.
Real payment collection (Stripe et al.) now, or manual bookkeeping first? No payment processor exists in the codebase today. Wiring one up is its own project (PCI scope, webhooks, invoicing, dunning). A manual ledger — superadmin logs "Acme Corp paid $499 on Aug 1" and logs expenses like hosting/dev cost — gets you the profit dashboard immediately with a fraction of the effort. Default assumed below: manual income/expense ledger first (Phase 2); real payment processing is a distinct, later project if you want self-serve billing.
Should client creation / client-to-staff assignment become owner-only by default, or owner-configurable? Your scenario says both things in different places ("only the owner can assign clients" and "owner can restrict/allow access"). Default assumed below: configurable per role, defaulting to "staff can create clients" preserved for Member/Viewer/Accountant-type roles but off for a fresh custom role — so the owner explicitly grants it rather than it being hardcoded either way.

4 Phased build plan

Phase 1 comes first because seat enforcement, finance visibility, and client-assignment restrictions are all easiest to bolt onto the new permission layer rather than the old scattered role checks.

Phase 1 — Roles & permissions engine

Large · 2–4 weeks

Foundation everything else in the scenario sits on top of: custom role types, owner-configurable visibility, consistent client-assignment scoping, owner-only vs. staff-allowed actions.

Backend

  • Migration: roles, permissions, role_permissions tables; seed the fixed permission catalogue; seed built-in roles (Owner, Admin, Manager, Clerk Admin, Accountant, User, Viewer) with sensible default grants
  • Add profiles.role_id, backfill from the existing 4-value enum, keep the enum column temporarily for the owner/superadmin distinction
  • New shared dependency in deps.py: require_permission("clients.manage") style checks, replacing scattered role-string comparisons
  • Refactor the ~8 files with ad-hoc role checks (admin.py, imports.py, task_attachments.py, clients.py, team.py, users.py, accounts.py, local_auth.py) to use it
  • Make the client-ownership scoping (today only in clients.py) reusable and apply it to client-services and tasks routers too — closes the gap flagged in §1
  • New endpoints: CRUD for a tenant's roles, GET permission catalogue, PATCH role_permissions

Frontend

  • New "Roles & Permissions" page under Owner settings — list built-in roles, toggle permissions per role
  • Role picker on the staff-creation/edit form (accountant-modal.tsx) switches from the fixed 4-option dropdown to the tenant's role list
  • Shared usePermissions() hook (new) replacing ad-hoc role === "admin" checks across the ~8 files that do it today (users-client.tsx, team-client.tsx, accountant-modal.tsx, clients-client.tsx, shell.tsx, session.tsx, etc.)
  • Nav/section visibility driven by permission flags instead of hardcoded role name comparisons
≈ 1 migration · ~9 backend files · ~9 frontend files · 2 new pages

Phase 2 — Seats & provider finance

Medium · 1–2 weeks

Turns the existing decorative seats/plan fields into real enforcement, and gives you the profit/expense visibility you described — independent of Phase 1, but the "who's allowed to see the finance page" check is cleaner once permissions exist.

Backend

  • Migration: platform_expenses, platform_income tables; add client_seats key to Tenant.settings
  • Enforcement check on staff-invite and client-create endpoints: count active usage vs. seat cap, 403 with a clear message when exceeded
  • New platform_finance.py router: CRUD for expenses/income, a summary endpoint (income − expenses, by month/category)
  • Extend tenant edit endpoint so superadmin sets purchased seats when a company buys more

Frontend

  • New superadmin "Finance" page: expense list/entry form, income list/entry form, profit summary chart
  • Seat usage indicator on the tenant detail page ("14/20 staff seats, 340/500 client seats") and a lighter version on the owner's own Team page
  • Friendly "seat limit reached, contact your provider" message when a staff/client creation is blocked
≈ 1 migration · ~5 backend files · ~5 frontend files · 1 new page

Phase 3 — Unified cross-tenant accounts console

Small–Medium · 3–7 days

Right now, seeing or editing a specific tenant's people means impersonating that tenant first. This phase adds direct-by-ID operations so the provider dashboard behaves like one console instead of "switch into each company one at a time."

Backend

  • New search endpoint: accounts across all tenants, filterable by name/email/role/tenant, without requiring impersonation
  • Extend credential-reset/suspend actions to accept an explicit tenant_id + profile_id instead of relying on the impersonation-derived tenant context

Frontend

  • New "Accounts" directory page in the superadmin console: searchable table of every owner/admin/staff/client across all companies, with inline suspend/reset actions
≈ no migration · ~3 backend files · ~3 frontend files · 1 new page

Phase 4 — Hardening

Small · 2–4 days

Cleanup and a safety pass once the new surfaces exist.

Backend

  • Tenant-isolation audit of every new table/endpoint from Phases 1–3 (confirm tenant_id scoping, confirm cross-tenant references are rejected the way tasks already do)
  • Optional: explicit no-email flag on the reissue endpoints, for UI clarity

Frontend

  • Remove any leftover hardcoded role checks the Phase 1 refactor missed
audit pass, no fixed file count

5 Risk & migration notes

Enum → table migrationThe role column is a native Postgres enum type today, referenced directly by type in models.py/schemas.py. Moving to a role_id FK means a backfill migration (map each existing owner/admin/member/viewer value to the matching seeded built-in role row) that must run before the old enum column is ever dropped — plan for a transition period where both columns exist, not a single atomic cutover.
Owner/superadmin stay specialRecommend keeping role="owner" and is_superadmin as they are (not folded into the new permissions table) — they're structural (only an Owner can manage billing/roles/seats for their own company; only a superadmin operates across companies), not something an Owner should be able to accidentally reconfigure into a limited role for themselves.
Don't let seat enforcement break existing tenantsEvery current tenant already has staff/clients created under the old soft-cap system. Before turning enforcement on, backfill each tenant's seats/client_seats to at least their current usage, or the first Phase 2 deploy will lock existing companies out of creating anything new.
SequencingPhase 1 is the one worth doing first and fully, even though it's the largest — Phases 2 and 3 both want "does this staff member have billing.view / accounts.manage permission" checks, and building those against the old ad-hoc role strings just means redoing the check a second time once Phase 1 lands.
