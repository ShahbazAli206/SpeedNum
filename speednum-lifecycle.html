1 Roles — two independent axes

There is no single flat "role" list. A profile has a tenant-scoped role enum and an independent, cross-tenant is_superadmin flag. A "client" is a separate concept again — it's whether client_id is set on the login.

is_superadmin = true

Superadmin

Platform-wide, cross-tenant. Creates/suspends/deletes firms, is the only one who can use /users, can impersonate any tenant.

role = owner

Owner

Full control of their one firm. Sees the whole book regardless of assignment. Only role (besides superadmin) that can create other staff.

role = admin

Admin

Restricted firm staff — scoped to only the clients assigned to them (owner_id). /team and /users are hidden from them.

role = member

Member

Ordinary accountant login. Tenant-wide read/write on the book, same as Owner minus staff-management rights.

role = viewer

Viewer

Read-oriented staff role. Same tenant-wide visibility as Member; no distinct extra restriction found.

client_id set

Client-portal user

Not a "role" value — any profile pinned to one client. Always forced to role="member" internally. Can only see its own client's books.

4 Client assignment & visibility scoping

Two separate "assignment" fields exist, and only one of them is actually access-controlled.

clients.owner_id

the assigned accountant / relationship owner. Set via ClientCreate/ClientUpdate.owner_id by any staff member.

→gates visibility
_owner_scope (clients.py:45-56)

if caller.role == "admin" (and not superadmin): filter to Client.owner_id == caller.id. Everyone else sees the whole book.

→
Applies to

all of /clients/* — list, get, patch, delete, portal-invite, contacts, client-services sub-routes.

client_services.assignee_id

separate field — who does the actual work for one client↔service pairing. Independent of owner_id.

→
No ownership check

set via POST /clients/{id}/services or POST /client-services — any staff can assign any staff, regardless of who owns the client.

Import behaviourBulk client imports resolve an accountant-name column to owner_id. If the name doesn't match anyone, the row still imports (commit 6b28de5) — owner_id is just left unset and the original text is preserved under Client.custom, instead of blocking the row.

5 Services — a tenant-wide catalogue

Unlike clients, services carry no owner/creator scoping — every staff role sees and edits the same catalogue.

Service

tenant-wide catalogue item: code, name, category, frequency, default_price, due_rule (JSON), lead_time_days. Unique per (tenant, code).

→assigned to
client_services (join)

per-client overrides: price, frequency_override, assignee_id, start/end date, is_active.

→projects
Deadlines

auto-generated the moment a service is assigned to a client (one per client_service × period_end), status: open · snoozed · filed · dismissed.

Project

optional service_id link — a project can represent one instance of doing a service for a client.

→
Task

no direct service_id — reaches a service only through its project, one hop away. client_id auto-fills from the project if omitted.

A default Canadian service catalogue can be re-seeded any time via POST /services/seed-defaults (Owner/Admin/Superadmin only) — it also runs automatically when a new tenant is provisioned.

6 Tasks — status lifecycle

Any staff role can create, assign, and move a task. There is no client-ownership restriction on tasks — flagged in §8.

todo→ in_progress→ review→ complete
blocked — a side-state reachable from in_progress or review, not part of the main chain
Mechanics Moved via PATCH /tasks/{id} (status field) or the kanban-specific POST /tasks/{id}/move (also re-indexes sibling position). Entering complete stamps completed_at; leaving it clears that stamp. Assigning/reassigning assignee_id always fires an in-app notification, plus email if configured.

7 Other lifecycles

Staff invitations

Owner/Superadmin sends invite→ token, 14-day expiry→ recipient accepts→ profile gets tenant + role

Can be revoked before acceptance. team.py:420-538

Impersonation

superadmin picks a tenant→ POST /admin/tenants/{id}/impersonate→ short-lived token, act_as_tenant claim→ acts as that firm

Audit rows always record the real superadmin's identity. deps.py:121-135, admin.py:440-470

Tenant (firm) lifecycle

create→ edit plan / caps→ suspend→ reactivate→ delete (cascade)

Suspended tenant's logins are rejected at sign-in. Superadmin console only. admin.py

temp password issued→ must_change_password = true→ blocked until POST /auth/complete-password-change

Enforced separately for tenant users and superadmins. deps.py:162-177, 257-268

8 Known inconsistencies worth knowing

Admin scoping is not applied everywhere _owner_scope (the rule that limits a plain Admin to only their own clients) is defined locally in clients.py and only guards /clients/* routes. It is not reused by /client-services (services.py) or /tasks//projects (workflows.py) — so a restricted Admin's client list is scoped on the Clients page, but the same Admin can still see and act on every client's service-assignments and tasks through those two surfaces.
"Users" vs "Accountants" vs "Clients" These are three different things sharing the same underlying profiles table: Accountants (/team) = staff rows (client_id IS NULL), any of the 4 roles. Users (/users, superadmin-only) = every profile, staff and client-portal alike. Clients (/clients) = the firm's own customer records in a completely separate table — a client can exist with zero login at all.
